# 通用代码规范

> 本文档定义了项目跨模块通用的编码美学、元数据标准及环境自检规约。

## 1. 文件头注释标准 (File Header)

新建任何源代码文件（Kotlin/Swift）时，**必须**包含标准的类注释头。

### 1.1 模板要求
```kotlin
/**
 * @Description: [简述类或文件的职责，须结合架构上下文]
 * @Author:         [动态获取 git config user.name]
 * @CreateDate:     [动态获取当前时间，格式：YYYY/MM/DD HH:MM]
 */
```

### 1.2 强制约束
- **Author 真实性**：优先从环境 `git config user.name` 获取。**严禁**使用 `admin`、`staff`、拼音缩写（如 `fanj`）等非真实姓名。
- **时间动态化**：`@CreateDate` 必须通过系统命令（如 `date`）实时获取，禁止硬编码或使用过时占位符。
- **标签清理**：**严禁**出现 `@Version` 标签，除非用户明确要求。
- **描述质量**：`@Description` 必须清晰描述该文件在项目中的职责，禁止留空。

## 2. API 注释边界

新增或修改对业务方可见的公共 API、状态模型、结果模型时，必须补齐 KDoc 注释：

- `expect` 公共 API 的方法必须说明业务语义、关键参数、返回值与调用时机。
- sealed class 状态分支必须说明状态含义；携带字段的分支必须说明字段来源和用途。
- 结果模型字段必须说明含义，尤其是 `code`、`message`、`raw` 等用于联调排障的字段。
- 注释必须服务调用方理解，禁止只重复方法名或写空泛描述。

平台实现注释边界：

- Android/iOS `actual` 普通方法默认不写逐方法 KDoc，避免机械重复 common API 语义。
- 只有存在特殊平台行为、SDK 限制、线程要求、生命周期约束或容易误用的配置时，才在 `actual` 实现中补充简短注释。
- 私有 helper 默认不写注释；只有映射逻辑复杂、规则来自 SDK 文档或存在反直觉分支时才补充。
- 平台实现中的必要注释应贴近特殊代码行，而不是整段重复公共 API 注释。

## 3. 公共模型序列化规范

新增或修改会暴露给业务层、跨模块传递、持久化、路由传参、网络传输或 JSBridge 交互的模型时，必须默认补齐 `kotlinx.serialization.Serializable`。

适用对象包括：
- `data class`、普通 `class` 结果模型。
- sealed class 状态模型及其子类型。
- SDK common 层暴露给业务使用的参数模型、结果模型、回调状态模型。
- 协议项、链接项、配置项等需要跨层传递的轻量模型。

只有模型明确只在平台实现内部使用、不会跨模块或跨边界传递时，才可以不加 `@Serializable`。

## 4. 环境自检规约 (Environment Self-Check)

AI 在执行编码任务（Phase 4）前，必须进行以下环境核对：

1.  **Git 身份核对**：通过 `run_shell_command` 执行 `git config user.name`。
    - 若获取到的名称为缩写或非真实姓名，必须使用 `ask_user` 询问用户真实姓名，并引导用户更新全局 Git 配置。
2.  **动态变量注入**：所有注释字段必须在写入前实时生成，确保信息的准确性。

## 5. 命名与工程美学

- **资源对齐**：所有新增文件必须遵循 `skills/资源与切图规范.md` 中的命名与 Import 规则。
- **架构一致性**：业务页面必须遵循 `standards/UI开发规范.md` 的红线以及 `knowledge/UI组件手册.md` 的 Screen/ScreenModel 结构。
