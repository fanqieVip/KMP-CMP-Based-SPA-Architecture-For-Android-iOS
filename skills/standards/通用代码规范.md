# 通用代码规范

> 本文档定义了项目跨模块通用的编码美学、元数据标准及环境自检规约。

## 1. 文件头注释标准 (File Header)

新建任何源代码文件（Kotlin/Swift）时，**必须**包含标准的类注释头。

### 1.1 模板要求
```kotlin
/**
 * @Description: [简述类或文件的职责，须结合架构上下文]
 * @Author:         [动态获取 git config user.name]
 * @CreateDate:     [动态获取当前时间，格式：YYYY/MM/DD HH:MM]
 */
```

### 1.2 强制约束
- **Author 真实性**：优先从环境 `git config user.name` 获取。**严禁**使用 `admin`、`staff`、拼音缩写（如 `fanj`）等非真实姓名。
- **时间动态化**：`@CreateDate` 必须通过系统命令（如 `date`）实时获取，禁止硬编码或使用过时占位符。
- **标签清理**：**严禁**出现 `@Version` 标签，除非用户明确要求。
- **描述质量**：`@Description` 必须清晰描述该文件在项目中的职责，禁止留空。

## 2. API 注释与文档标准

项目强制执行 KDoc 文档校验，任何非重写、非自动生成的代码元素都必须具备文档说明。

### 2.1 类注释规范
- **所有类**：必须包含 `/** ... */` 格式的 KDoc 类注释。
- **构造器属性**：如果构造函数中使用 `val/var` 声明了属性，**必须**在类注释中通过 `@param <参数名>` 逐一进行业务说明。

### 2.2 方法注释规范
- **全量覆盖**：所有非重写方法、顶级函数（Top-level Function）必须包含 `/** ... */`。
- **参数说明**：每一个参数必须在 KDoc 中通过 `@param` 标注含义。
- **返回值说明**：若方法有返回值（非 `Unit`），必须包含 `@return` 描述。

### 2.3 成员变量规范
- **类体内变量**：定义在类花括号 `{}` 内部的非重写成员变量，必须包含注释（支持 `/** */` 或 `//`）。
- **逻辑隔离**：构造参数已在类头标注，类体内变量需独立标注，确保代码自解释。

## 3. 架构红线校验 (com.basic.lint)

项目使用自定义 Gradle 插件在编译期强制拦截违反架构设计的代码。

| 目标类型 | 校验项 | 禁止项 | 理由 |
| --- | --- | --- | --- |
| `Screen` 子类 | 构造函数参数 | 包含任何函数类型（Lambda）参数 | Screen 必须支持 URL 序列化。Lambda 无法通过 URL 传递。 |
| `ScreenModel` 子类 | 构造函数参数 | 包含任何函数类型（Lambda）参数 | 防止 ScreenModel 长期持有外部 UI 组件引用，导致内存泄漏。 |
| `Dialog` / `NativeDialog` | 构造函数参数 | 使用 `val`/`var` 声明函数属性 | 函数属性会长期持有外部引用。强制去掉属性关键字，并改用 `by autoClear` 委托。 |
| Composable 作用域 | 函数调用 | 直接调用 `rememberScreenModel()` | 无法触发 `onInit` 等生命周期映射。必须统一使用 `rememberBaseScreenModel()`。 |
| 类定义 | 继承关系 | 直接继承 `io.github.hristogochev.vortex.screen.Screen` | 无法享受 `BaseScreen` 提供的状态栏管理、Trace 注入等能力。 |
| Screen 实现类 | 类注解 | 缺少 `@Router` 注解 | 所有的非抽象 Screen 必须注册路由路径以支持跨模块跳转。 |
| Screen 实现类 | 构造函数参数 | 缺少 `@Params` 注解 | 所有的非抽象 Screen 构造参数必须显式声明 URL 映射。 |
| 存储访问 | `import` 引用 | 直接使用 `com.russhwolf.settings.Settings` | 必须统一使用 `core/base` 提供的响应式封装（`asFlowXXX`）。 |
| 网络 API | 类命名 | Ktorfit API 接口名字未以 `Api` 结尾 | 统一项目命名语义。 |
| 组件命名 | 后缀校验 | 未以 `Screen`, `ScreenModel`, `Dialog`, `NativeDialog` 结尾 | 增强代码可读性与组件识别度。 |
| 网络 API | 访问隔离 | 在非 Repository 类中持有 API 实例 | 网络请求细节必须封装在 Repository 中。非 `*Repository` 结尾的类禁止持有 API 成员。 |
| 网络 API | 访问隔离 | 在 Repository 中 API 实例非 `private` | 防止原始 API 接口泄露到外部。 |

## 4. 公共模型序列化规范

新增或修改会暴露给业务层、跨模块传递、持久化、路由传参、网络传输或 JSBridge 交互的模型时，必须默认补齐 `kotlinx.serialization.Serializable`。

适用对象包括：
- `data class`、普通 `class` 结果模型。
- sealed class 状态模型及其子类型。
- SDK common 层暴露给业务使用的参数模型、结果模型、回调状态模型。
- 协议项、链接项、配置项等需要跨层传递的轻量模型。

## 5. 环境自检规约 (Environment Self-Check)

AI 在执行编码任务前，必须进行以下环境核对：

1.  **Git 身份核对**：执行 `git config user.name`，确保 Author 信息的真实性。
2.  **动态变量注入**：所有注释字段（Description, Author, Date）必须实时生成。
3.  **Lint 预检**：提交代码前应自检是否违反上述架构红线，确保能够通过 KSP 编译审计。

## 6. 命名与工程美学

- **资源对齐**：所有新增文件必须遵循 `skills/资源与切图规范.md` 中的命名与 Import 规则。
- **架构一致性**：业务页面必须遵循 `knowledge/UI组件手册.md` 的 Screen/ScreenModel 结构。
- **排除规则**：Lint 插件会自动跳过枚举类（Enum）、KSP/Ktorfit 自动生成的代码（build/generated 目录），开发者无需处理这些位置。
