## 1. 项目定位

KmpProject 是一个 Kotlin Multiplatform + Compose Multiplatform 移动端基础工程，目标平台为 Android 与 iOS。

核心能力包括：

- 跨端 Compose UI 与 Vortex Screen 导航。
- Koin + 自定义 SPI 注册中心的跨模块服务发现。
- Ktor + Ktorfit 网络层。
- 响应式持久化数据、全局状态、Toast、弹窗、下载器、WebView/JSBridge。
- Android 安全加密与运行环境校验能力，iOS 使用空实现或 Kotlin 实现占位。
- Android 原生壳与 iOS SwiftUI 壳接入同一个 KMP Compose 入口。

### 2.1 buildSrc 内部构建逻辑约定

本项目的 `buildSrc` 用于承载当前仓库内部构建逻辑，包括 Gradle 插件、KSP/编译期 processor、构建脚本工具类、打包、环境、资源处理、上传、通知等内部任务逻辑。

判断规则：

- 只服务当前仓库、不对外发布、不作为跨仓库稳定 API 复用的构建工具，可以优先收敛进 `buildSrc`。
- 不得机械套用“processor 必须独立发布模块”的通用建议；应先确认项目是否需要独立版本生命周期或跨仓库复用。
- `buildSrc` 方案允许牺牲部分 classpath 纯净度，但必须换来明确收益，例如根工程模块列表简洁、内部构建逻辑集中、业务侧接入无感。
- 如果未来某个 processor 或插件需要跨仓库复用、版本化发布或独立生命周期，再重新评估拆出 included build 或独立发布模块。

KSP processor 收敛进 `buildSrc` 时必须满足：

- processor provider 必须保留 `META-INF/services/com.google.devtools.ksp.processing.SymbolProcessorProvider`。
- service 文件内容必须指向真实 provider 类。
- 使用方 KSP 配置必须拿到 `buildSrc` 产出的 jar 或等价 processor classpath。
- 迁移后必须删除根工程中不再需要的构建辅助 include，避免业务模块列表残留无效模块。
- 验证至少包含：`buildSrc` 能编译出 jar、service loader 文件被打入 jar、使用方 KSP 任务能发现 processor、生成代码路径和业务 import 不变。

## 5. UI 与导航架构

### 5.1 顶层 Compose 入口

`App()` 是共享 UI 入口：

```kotlin
@Composable
fun App(
    screen: () -> Screen = { SplashScreen() },
    uiContainer: UIContainer,
    permissionController: PermissionController
)
```

调用链：

```text
App()
  -> BaseApp()
       -> AutoSize()
       -> CompositionLocalProvider(LocalAppState, LocalPermissionController, LocalUIContainer)
       -> MaterialTheme
       -> UIConfigService.RootUiConfig(content)
       -> Navigator(initial Screen)
       -> CurrentScreen / CurrentScreenPredictiveBack
       -> BuildToast()
       -> AutoScreenOrientation()
```

`BaseApp` 是底层统一入口，业务公共层不要再额外包一层 `BasicApp`。需要在 common 层统一定制根 UI 时，通过 `UIConfigService.RootUiConfig(content)` 注入，例如全局样式、Toast 展示或根布局包裹；没有注册 `UIConfigService` 时，`BaseApp` 直接执行默认根 UI。

### 5.2 Screen 基类

业务页面通常继承：

```text
BasicScreen -> BaseScreen -> Vortex Screen
```

`BaseScreen` 统一处理：

- `key = uniqueScreenKey()`，避免混淆后状态保存异常。
- 状态栏文字颜色与屏幕方向。
- 返回拦截 `BaseScreen.CanBackHandler(...)`。
- `ScreenContext` 注入。
- `DialogController` 注入和弹窗栈渲染。
- 链路来源注入：页面内容会被 `DefaultTraceInfoScope(fromTraceId, null)` 包裹。
- iOS 返回手势抖动规避。

业务页面只需要实现：

```kotlin
@Composable
override fun CreateUI()
```

### 5.3 页面与弹窗链路作用域

`LocalTraceInfo` 是一个基于 Compose `staticCompositionLocalOf` 的局部链路上下文，用于在 Screen、Dialog、NativeDialog 之间传递“当前页面从哪里来”和“下级页面应该归到哪条新链路”。

核心数据结构：

```text
TraceInfo(
  fromId = 当前 UI 所属链路来源,
  currentId = 当前作用域中新起的链路
)
```

读取规则：

- `LocalTraceInfo.current?.getFromTraceId()`：获取当前 UI 的所属链路来源，主要用于埋点。
- `LocalTraceInfo.current?.getTransitiveTraceId()`：获取要传给下级 Screen 或 Dialog 的链路；优先返回 `currentId`，没有新链路时回退到 `fromId`。

作用域来源：

```text
BaseScreen.Content()
  -> DefaultTraceInfoScope(fromTraceId, null)
  -> CreateUI()

Dialog / NativeDialog
  -> DefaultTraceInfoScope(fromTraceId, null)
  -> CreateUI()
```

`DefaultTraceInfoScope` 是基础层内部 API，负责把外部传入的 `fromTraceId` 注入到当前 UI 子树。业务代码需要开启一段新链路时，使用公开的 `TraceInfoScope(newTraceId) { ... }`：

```kotlin
TraceInfoScope(newTraceId = "home_card_banner") {
    val traceInfo = LocalTraceInfo.current
    val fromTraceId = traceInfo?.getFromTraceId()
    val childTraceId = traceInfo?.getTransitiveTraceId()
}
```

`TraceInfoScope` 会继承父级 `fromId`，并把 `newTraceId` 作为当前作用域的 `currentId`。因此当前作用域内做埋点仍然读取父级来源，打开下级页面或弹窗时则传递新链路。

导航与弹窗传递方式：

```kotlin
val traceId = LocalTraceInfo.current?.getTransitiveTraceId()
navigator.push(DetailScreen(), traceId)
LocalDialogController.current.showNow(ConfirmDialog(), traceId)
NativeConfirmDialog().show(LocalUIContainer.current, traceId)
```

`NavigatorKtx.kt` 为 Vortex `Navigator` 扩展了带 `traceId` 的 `push`、`replace`、`replaceAll`、`replaceUntil`。这些扩展只会在目标 `Screen` 是 `BaseScreen` 时写入 `fromTraceId`，然后再调用原始 Vortex 导航 API。弹窗侧通过 `DialogController.showNow/showPriority/showMaxPriority(..., traceId)` 或 `NativeDialog.show(..., traceId)` 写入 `fromTraceId`。

链路框架只负责 UI 层上下文传递，不负责生成 traceId，也不负责上报埋点；traceId 命名、生成和埋点上报由业务侧决定。

### 5.4 ScreenModel 生命周期

`MainScreenModel` 是页面主状态模型，约定一个 Screen 原则上只有一个主模型。

生命周期顺序：

```text
rememberMainScreenModel(...)
  -> 首次可见: onInit(context)
  -> 首次可见: onLoad(context)
  -> 每次可见: onVisible(context)
  -> 不可见: onInvisible(context)
  -> dispose: onDestroyed()
```

页面 UI 状态：

- `uiLoading(text)`
- `uiSuccess(empty = false)`
- `uiError(code, error)`
- `showPopLoading(info)`
- `dismissPopLoading()`

公共 UI 封装：

- `BasicInteraction(...)`：加载、错误、空页面、弹窗 loading。
- `BasicRefreshLazyListInteraction(...)`：列表下拉刷新/上拉加载。
- `BasicRefreshLazyGridInteraction(...)`：网格刷新/分页。

分页控制不再依赖专用分页模型，而是由 ScreenModel 实现 `PagingControl` 协议：

```kotlin
class XxxScreenModel : BasicScreenModel(), PagingControl {
    override val refreshState = RefreshState(true, true)

    override suspend fun pagingFirst() {
        // 首次加载或下拉刷新
    }

    override suspend fun pagingMore() {
        // 上拉加载更多
    }
}
```

`MainScreenModel` 在页面首次可见初始化后会检测当前模型是否实现 `PagingControl`。如果实现了该协议，框架会自动监听 `refreshState.state`，并在下拉刷新时触发 `pagingFirst()`、上拉加载时触发 `pagingMore()`。业务加载完成后调用 `pagingOver(isOver)` 更新是否还有更多数据。

## 6. URL 路由插件架构

项目当前使用基于 KSP 的 URL 路由插件，把跨模块页面发现与参数解析从手写 `ProjectRouterImpl` 中拆出。`ProjectRouterImpl` 属于旧方案，不再作为新增路由的设计入口。

核心目标：

- 支持没有直接依赖关系的模块通过 URL 跳转到目标 `Screen`。
- 调用方只需要 `asRouter("project/main?id=13&name=hello")` 获取 `Screen` 实例，再交给现有 Vortex `navigator` 执行跳转。
- 页面构造参数由 KSP 生成代码解析，不依赖运行时反射，兼容 Android 与 iOS。

### 6.1 注解入口

路由页面使用 `@Router` 标记路径，构造参数使用 `@Params` 标记 URL query key：

```kotlin
@Router("project/main")
class MainScreen(
    @Params("id") val id: Int? = null,
    @Params("name", autoDecode = true) val name: String? = null,
    @Params("bean", jsonTarget = MainBean::class, autoDecode = true) val bean: MainBean? = null
) : BasicScreen()
```

`@Router` 只允许标记 `io.github.hristogochev.vortex.screen.Screen` 子类。被标记类如果不是 `Screen`，KSP 编译阶段会报错。

### 6.2 生成链路

路由插件由两部分组成：

- `buildSrc/src/main/kotlin/com/frame/basic/plugin/RouterPlugin.kt`
  - 自动应用 KSP。
  - 向 `kspCommonMainMetadata` 添加 `buildSrc/build/libs/buildSrc.jar`，让 KSP 通过 service loader 发现内部路由 processor。
  - 注册手动任务 `generateBuildRouter`。
- `buildSrc/src/main/kotlin/com/frame/basic/router/`
  - 扫描 `commonMain` 中的 `@Router`。
  - 生成 `RouteRegistry` 与对应 Koin `Module`。
  - 通过 `buildSrc/src/main/resources/META-INF/services/com.google.devtools.ksp.processing.SymbolProcessorProvider` 注册 provider。
  - 输出目录为 KSP 标准目录：`build/generated/ksp/metadata/commonMain/kotlin/...`。

注意：路由 processor 属于本仓库内部构建能力，当前不对外发布，按 `buildSrc` 内部构建逻辑约定收敛在 `buildSrc`。迁移或调整时不得遗漏 service loader 文件，否则 KSP 无法发现 provider。

生成产物示例：

```kotlin
object MainRouteRegistry : RouteRegistry {
    override fun routes(): List<RouteEntry> = listOf(
        RouteEntry("project/main") { request ->
            MainScreen(
                id = request.int("id"),
                name = request.string("name", autoDecode = true)
            )
        }
    )
}

val mainRouteModule: Module = module {
    single<RouteRegistry>(qualifier = named("mainRouteRegistry")) { MainRouteRegistry }
}
```

模块需要把生成的 route module include 到自身 Koin module：

```kotlin
val projectModule = module {
    includes(mainRouteModule)
    registerSPI<ApplicationService> { ApplicationServiceImpl() }
}
```

### 6.3 调用链路

```text
asRouter(url)
  -> parseRouteUrl(url)
  -> RouteRegistryStore.find(path)
       -> 从 Koin 加载所有 RouteRegistry
  -> RouteEntry.factory(RouteRequest)
  -> 返回 Screen?
  -> navigator.push/replace(screen)
```

调用示例：

```kotlin
val screen = asRouter("project/main?id=13&name=hello")
screen?.let { navigator.push(it) }
```

`asRouter` 只负责把 URL 转成 `Screen?`，不直接执行导航。

### 6.4 参数约束

基础类型仅支持：

- `String`
- `Int`
- `Long`
- `Float`
- `Double`
- `Boolean`

非基础类型必须使用 `jsonTarget`，且 `jsonTarget` 类型必须与构造参数类型完全一致，父子类型也不允许。

```kotlin
@Serializable
data class UserParam(val id: String)

@Router("user/detail")
class UserDetailScreen(
    @Params("user", jsonTarget = UserParam::class) val user: UserParam? = null
) : BasicScreen()
```

KSP 编译期校验规则：

- `@Router` 类必须是 `Screen`。
- 非基础类型如果没有匹配的 `jsonTarget`，报错。
- `jsonTarget` 与参数类型不完全一致，报错。
- 构造参数没有默认值且没有 `@Params`，报错。
- `@Params` 标记的非空参数如果没有默认值，报错。
- `autoDecode = true` 只允许用于 `String` 参数或声明了 `jsonTarget` 的参数。
- `@Router` 类没有构造参数时不报错。

运行时参数规则：

- URL 未传某个 key 时，如果构造参数有默认值，则使用默认值。
- URL 未传某个 key 且参数可空无默认值时，传入 `null`。
- URL 传入 `key=` 空值时，按 `null` 处理。
- 基础类型解析失败时按 `null` 处理，若参数有默认值则使用默认值。

### 6.5 URL 编码约定

默认情况下，路由不会自动解码 query value。只有 `@Params(autoDecode = true)` 的 `String` 参数和 `jsonTarget` 参数会使用 Ktor `decodeURLQueryComponent()` 解码。

传递包含 `?`、`&`、`=`、中文、JSON 等特殊字符的 query value 时，调用方必须先编码参数值：

```kotlin
val name = "https://xxxx.com"
    .encodeURLParameter()

asRouter("project/main?name=$name")
```

不要用 `encodeURLQueryComponent()` 的默认行为编码完整参数值。它默认 `encodeFull = false`，会保留 `?`、`&`、`=` 等 URL 结构字符，容易导致 query 被提前截断。需要使用 Ktor `encodeURLParameter()`，或显式使用 `encodeURLQueryComponent(encodeFull = true)`。

### 6.6 手动生成任务

插件不会在 Gradle sync 阶段写占位文件。路由代码在 build/KSP 阶段生成，也可以手动执行：

```bash
./gradlew :project:main:generateBuildRouter
```

## 7. DI 与 SPI

项目使用 Koin 启动模块，但服务获取不直接通过 Koin 注入，而是通过自定义 `SPIRegisterCenter`。

核心结构：

```text
registerSPI<T> { impl }
  -> SPIRegisterCenter.register(T::class, impl())

withImpl<T>()
  -> SPIRegisterCenter.first<T>()

SPIRegisterCenter.all<T>()
  -> 返回所有同类型实现
```

当前注册模块：

| Module | 注册服务 |
| --- | --- |
| `commonModule` | `ApplicationService -> common.ApplicationServiceImpl`、`UIConfigService -> UIConfigServiceImpl` |
| `projectModule` | `includes(mainRouteModule)`、旧 `ProjectRouter -> ProjectRouterImpl`、`ApplicationService -> project.ApplicationServiceImpl`、`ProjectService -> ProjectServiceImpl` |

`ApplicationProxyManager` 使用 `SPIRegisterCenter.all<ApplicationService>()` 聚合所有应用生命周期实现。

## 8. 网络架构

网络入口：

### 8.1 目录规范 (AI 强制遵循)
- **API (Ktorfit)**：统一下沉至 `core/common/src/commonMain/kotlin/com/basic/common/api/`。
- **Repository**：统一放至 `core/common/src/commonMain/kotlin/com/basic/common/repository/`。

## 11. WebView 与 JSBridge

核心类型：

- `WebViewState`
- `NativeWebView(modifier, state)`
- `IWebView` expect/actual
- `JsBridgeData`

持有规则：

- `WebViewState` 必须放在 `ScreenModel` 中，例如 `val webviewState = WebViewState(scope = screenModelScope)`。
- 不要在 Composable 中直接 `remember { WebViewState(...) }` 或直接创建原生 WebView 状态。Compose 重组、页面局部重建或 slot 变化可能导致 WebView 重新创建、重复加载 URL、JSBridge 重复注册。
- `ScreenModel.onDestroyed()` 中必须调用 `webviewState.destroyed()`，清空 JSBridge、回收原生 WebView，避免内存泄漏。
- 这个规则不只适用于 WebView。KMP 架构中加载任何有生命周期和资源占用的原生 UI 控件，都推荐把“原生控件状态/控制器”放进 `ScreenModel`，由 Compose 只负责渲染和转发事件，由 `ScreenModel.onDestroyed()` 统一释放。

调用方向：

```text
KMP -> WebView
  WebViewState.loadUrl/goBack/goForward/reload/stopLoading
  WebViewState.evaluateJavaScripts<T, R>(...)

WebView -> KMP
  JS 发送 JsBridgeData(callbackId, methodName, jsonParams)
  WebViewState.receiveJsMessage(...)
  WebViewState.registerJsBridge<T, R>(methodName) { ... }
```

推荐结构：

```text
WebviewScreen.CreateUI()
  -> rememberMainScreenModel { WebviewScreenModel() }
  -> NativeWebView(state = model.webviewState)

WebviewScreenModel
  -> val webviewState = WebViewState(scope = screenModelScope)
  -> onInit: webviewState.loadUrl(url)
  -> onDestroyed: webviewState.destroyed()
```

`project/main` 中 `WebviewScreen` 是使用示例。

## 13. Native 安全层

`core/native` 的调用链比较特殊：加解密的具体实现写在 `commonMain`，iOS 直接调用这份实现；Android 则先把 `androidNativeArm64Main` 编译成静态库，再在 Android 打包阶段通过 CMake 生成动态库和 JNI 桥接，最后由 `androidMain` 的 `EncryptJni` 映射到 JNI 方法。

公共 API 位于 `commonMain`：

```kotlin
expect object Encrypt {
    fun encodeData(data: String): String
    fun decodeData(data: String): String
    fun createSign(data: String): String
}

expect inline fun checkEnv()
```

实现与构建分工：

| Source set | 职责 | 关键文件 |
| --- | --- | --- |
| `commonMain` | 编写真正的加解密实现与公共 expect API。当前 `EncryptNativeImpl` 是加解密实现入口。 | `core/native/src/commonMain/kotlin/com/basic/native/Encrypt.kt` |
| `iosMain` | `actual object Encrypt` 直接调用 `EncryptNativeImpl`。 | `core/native/src/iosMain/kotlin/com/basic/native/Encrypt.ios.kt` |
| `androidNativeArm64Main` | `actual object Encrypt` 也直接调用 `EncryptNativeImpl`；同时提供 KNI/JNI 映射函数。手动执行 `:core:native:androidNativeArm64Binaries` 后，会在 `src/androidNativeArm64Main/staticLib/` 下生成 `libshared_nativeLibs.a` 和 API 头文件。 | `core/native/src/androidNativeArm64Main/kotlin/com/basic/native/Encrypt.androidNativeArm64.kt` |
| `androidMain` | 暴露给 Android JVM 层使用的 `actual object Encrypt`，通过 `EncryptJni` 调用 JNI 方法。 | `core/native/src/androidMain/kotlin/com/basic/native/Encrypt.android.kt`、`core/native/src/androidMain/kotlin/com/basic/native/utils/EncryptJni.kt` |
| `androidMain/cpp` | Android 打包时通过 CMake 把 `androidNativeArm64Main/staticLib/libshared_nativeLibs.a` 链接进 `shared_nativeLibs.so`，并生成可被 `EncryptJni.external` 映射的 JNI 动态库。 | `core/native/src/androidMain/cpp/CMakeLists.txt` |

Android 端完整调用与产物链路：

```text
开发/构建阶段：
commonMain EncryptNativeImpl
  -> androidNativeArm64Main KNI/JNI 映射函数
  -> 手动执行 :core:native:androidNativeArm64Binaries
  -> 生成 src/androidNativeArm64Main/staticLib/libshared_nativeLibs.a
  -> Android 打包时 CMake 链接 libshared_nativeLibs.a
  -> 生成 shared_nativeLibs.so

运行阶段：
业务代码调用 Encrypt.encodeData/decodeData/createSign
  -> androidMain actual Encrypt
  -> EncryptJni.external encodeData/decodeData/createSign
  -> System.loadLibrary("shared_nativeLibs")
  -> shared_nativeLibs.so 中的 JNI 桥接方法
  -> androidNativeArm64Main 映射函数
  -> checkEnv(source, bridge) 校验 JVM 桥接签名
  -> commonMain EncryptNativeImpl
```

注意点：

- `commonMain` 是算法实现源头，避免 iOS 与 Android native 分叉实现。
- `iosMain` 没有 JNI 链路，直接调用 `EncryptNativeImpl`。
- `androidNativeArm64Main` 不是 Android App 运行时直接调用层，它负责生成可被 CMake 链接的静态库。
- `androidMain` 只通过 `EncryptJni` 映射 JNI 方法，不直接调用 `EncryptNativeImpl`。
- 如果修改 `commonMain` 的加解密实现，Android native 静态库需要重新执行 `:core:native:androidNativeArm64Binaries` 生成，再进行 Android 打包。

Android `checkEnv()` 校验内容包括：

- APK 签名 SHA-1 派生值与 `BuildConfig_com_basic_nativeLibs.APK_VERIFY_CODE` 对比。
- Application 类路径存在性。
- 线程数量基础校验。
- NpManager、fancyBypass、SRPath、MT 管理器、插件化环境、系统服务 Hook、LSPatch 痕迹等检测。
- 30 秒内复用上次校验结果，减少频繁校验成本。

iOS 与 Android Native Arm64 中 `checkEnv()` 当前为空实现。

### 14.4 依赖库管理约定

本项目按“依赖归属模块就近配置”的方式管理 Android 与 iOS 依赖，避免把业务模块依赖集中堆到 `app` 或 `iosApp`。

本地依赖包约定：

- 模块专属 Android 本地依赖放在该模块的 `libs/android/` 下，例如 `.jar`、`.aar`。
- 模块专属 iOS 本地依赖放在该模块的 `libs/ios/` 下。
- 框架脚本会自动处理这些本地依赖的构建接入问题；新增本地包时优先放入所属模块，不要跨模块复用专属目录。

远程依赖包约定：

- 所有远程依赖都配置在实际使用它的模块 `build.gradle.kts` 中。
- Android/Maven 依赖写在对应 source set 的 dependencies 中。
- iOS Pod 依赖写在对应模块的 `cocoapods { pod(...) }` 中，且必须显式指定版本，避免 Pod 意外升级。
- 禁止在业务模块额外添加 framework 配置；Pod 配置会由根构建脚本自动同步到 `iosApp/Podfile`。

iOS framework 输出约束：

- 为避免 iOS 编译时出现链接库冲突或重复 framework 异常，全局只允许生成 `app` 模块中配置的 `ComposeApp` framework。
- `ComposeApp` framework 必须保持 `isStatic = true`，也就是静态库 framework。
- 其他共享模块只通过 `app` 模块依赖链参与编译，不单独对外生成 framework。

### 14.5 SDK key 配置与 iOS Info.plist 参数注入

三方 SDK 核心 key 的唯一来源是 `buildSrc/src/main/kotlin/com/frame/basic/buildsrc/SDKKeyConfig.kt`。

配置原则：

- 必须配置的核心参数，例如 `appId`、`appKey`、`secret`、iOS `universalLink` 等，按 SDK 和平台拆分到 `SDKKeyConfig.<Sdk>.Android` 与 `SDKKeyConfig.<Sdk>.IOS`。
- 各 `libs/<name>` SDK 模块通过 `BuildKonfig` 把本模块需要的 key 注入到模块内，运行期由 Android/iOS 各自 `actual` 实现读取。
- common API 不暴露必须核心 key，只保留运行时真正需要由业务传入的参数，例如渠道、授权状态、设备隐私参数等。
- 没有平台消费路径的配置不得定义，避免配置膨胀和误导。

本项目使用 `com.basic.ios` Gradle 插件统一管理三方 SDK 需要写入 iOS `Info.plist` 的 AppKey、AppId、URL Scheme 等参数。

核心原则：

- 凡是 SDK 要求在 iOS `Info.plist` 中配置的参数，优先通过 `com.basic.ios` 注入，不在 `Info.plist` 中硬编码真实值。
- 注入参数的唯一配置来源统一为 `buildSrc/src/main/kotlin/com/frame/basic/buildsrc/SDKKeyConfig.kt`。
- 参数声明放在对应 SDK 所属的 `libs/<name>/build.gradle.kts` 中，保持“谁接 SDK、谁声明 plist 字段”的模块归属。
- `iosApp/Configuration/Config.xcconfig` 只 include 一个统一生成文件：`iosConfig.xcconfig`。
- `iosApp/iosApp/Info.plist` 使用 Xcode build settings 展开语法读取变量，例如 `$(WECHAT_IOS_APP_ID)`。

配置链路：

```text
SDKKeyConfig
  -> libs/<name>/build.gradle.kts iosConfig { field(...) }
  -> com.basic.ios 聚合生成 iosApp/Configuration/iosConfig.xcconfig
  -> iosApp/Configuration/Config.xcconfig include
  -> Info.plist 中通过 $(KEY) 引用
```

插件行为：

- 在 macOS 上，Gradle Sync 完成后自动刷新 `iosConfig.xcconfig`。
- 显式执行 `generateIosConfig` 也会刷新该文件。
- 非 macOS 环境可以正常配置 DSL，但不会写 iOS 配置文件，避免 Android/CI 环境被 iOS 文件生成逻辑干扰。
- 多模块声明同名 key e且值不一致时会直接失败，避免静默覆盖。

## 17. 架构红线校验 (com.basic.lint)

项目使用自定义的 `com.basic.lint` Gradle 插件，通过 KSP 在编译期强制执行架构红线校验，以防止常见的内存泄漏和路由安全性问题。

### 17.1 核心红线规则

| 目标类型 | 校验项 | 禁止项 | 理由 |
| --- | --- | --- | --- |
| `Screen` 子类 | 构造函数参数 | 包含任何函数类型（Lambda）参数 | Screen 必须支持 URL 序列化以实现跨模块跳转。Lambda 无法通过 URL 传递。 |
| `ScreenModel` 子类 | 构造函数参数 | 包含任何函数类型（Lambda）参数 | 防止 ScreenModel 长期持有外部 UI 组件引用，导致严重的内存泄漏。 |
| `Dialog` / `NativeDialog` | 构造函数参数 | 使用 `val`/`var` 声明函数属性 | 函数属性会长期持有外部引用。强制去掉属性关键字，并改用 `by autoClear` 委托。 |
| Composable 作用域 | 函数调用 | 直接调用 `rememberScreenModel()` | 无法触发 `onInit/onLoad` 等生命周期映射。必须统一使用 `rememberMainScreenModel()`。 |
| 类定义 | 继承关系 | 直接继承 `io.github.hristogochev.vortex.screen.Screen` | 无法享受 `BaseScreen` 提供的状态栏管理、Trace 链路注入等能力。必须统一继承 `BaseScreen` 或 `BasicScreen`。 |
| Screen 实现类 | 类注解 | 缺少 `@Router` 注解 | 所有的非抽象 Screen 必须注册路由路径以支持跨模块跳转。 |
| Screen 实现类 | 构造函数参数 | 缺少 `@Params` 注解 | 所有的非抽象 Screen 构造参数必须显式声明 URL 映射，确保路由解析逻辑清晰、可控。 |
| 存储访问 | `import` 引用 | 直接使用 `com.russhwolf.settings.Settings` | 避免滥用原始存储 API。必须统一使用 `core/base` 提供的响应式封装（`asFlowXXX`），确保 UI 状态自动同步。 |
| 网络 API | 类命名 | Ktorfit API 接口名字未以 `Api`结尾 | 统一项目命名语义。检测到 Ktorfit 注解时强制要求 `Api` 后缀。 |
| Screen | 类命名 | 实现类未以 `Screen` 结尾 | 统一页面命名规范，增强代码可读性。 |
| ScreenModel | 类命名 | 实现类未以 `ScreenModel` 结尾 | 统一模型命名规范。 |
| Dialog | 类命名 | 实现类未以 `Dialog` 结尾 | 统一 Compose 弹窗命名规范。 |
| NativeDialog | 类命名 | 实现类未以 `NativeDialog` 结尾 | 统一原生弹窗命名规范。 |
| 所有类 | 类注释 | 缺少 KDoc 类注释 | 所有的类必须提供 `/** */` 描述。若包含构造参数属性，必须使用 `@param` 标注。 |
| 所有类 | 成员变量 | 缺少注释 | 类体内定义的非重写成员变量必须有注释 (支持 `/** */` 或 `//`)。 |
| 所有方法 | 方法注释 | 非重写方法缺少 KDoc 注释 | 非重写业务方法必须提供 `/** */` 描述，且参数必须有 `@param`，非 `Unit` 返回值必须有 `@return`。 |
| 网络 API | 访问隔离 | 在非 Repository 类中持有 API 实例 | 网络请求细节必须封装在 Repository 中。非 `*Repository` 结尾的类禁止持有 API 成员。 |
| 网络 API | 访问隔离 | 在 Repository 中 API 实例非 `private` | 防止原始 API 接口泄露到外部 ... |
| `Data Class` | 类注释 | 缺少 KDoc 类注释 | 所有数据模型必须有 `/** */`。若包含构造参数，必须使用 `@param` 标注每一项。 |
| `Data Class` | 成员变量 | 缺少注释 | 类体内定义的非重写成员变量必须有注释 (支持 `/** */` 或 `//`)。 |
| `Data Class` | 方法注释 | 非生成的自定义方法缺少 KDoc 注释 | 排除 `copy`, `toString` 等自动生成方法，业务自定义方法必须加注释。 |

### 17.2 接入方式

在模块的 `build.gradle.kts` 中应用插件：

### 17.3 校验机制
- **零配置生效**：插件会自动扫描模块内全量源码，无需在类上添加任何注解。
